# Repository Instructions

## Project

This is a FastAPI backend learning project built as a production-style application.

The project uses feature-oriented organization. Keep implementations practical and avoid unnecessary enterprise abstractions.

## Stack

- Python 3.13
- FastAPI
- Pydantic v2
- SQLAlchemy 2.x async
- asyncpg
- PostgreSQL
- Alembic
- pytest
- uv

Use current stable APIs and patterns for these libraries.

## Architecture

- Keep the project feature-oriented.
- Routers own HTTP concerns and translate domain errors into HTTP responses.
- Services own business logic and transaction orchestration.
- Repositories own database queries and persistence operations.
- Do not raise FastAPI `HTTPException` from services or repositories.
- Keep framework-specific concerns at the API boundary when practical.
- Avoid adding abstraction layers without a concrete responsibility.
- Follow existing project conventions unless there is a clear technical reason to change them.
- Do not rewrite working code only to impose a different style.

## Database

- Use SQLAlchemy 2.x APIs.
- Use `AsyncSession` for database access.
- Prefer modern `select()`-based SQLAlchemy patterns.
- Database schema changes require Alembic migrations.
- Review autogenerated migrations before applying them.
- Do not blindly apply an autogenerated migration if it changes unrelated tables or columns.
- Do not manually modify the database schema outside migrations except for explicit local debugging or learning tasks.
- Keep transaction ownership in the service layer unless the existing design explicitly requires otherwise.

## Security

- Never store plaintext passwords.
- Never commit secrets, credentials, tokens, or `.env` files.
- Never expose password hashes in API responses.
- Never print secret values in logs, responses, or implementation reports.
- Authentication failures should not unnecessarily reveal whether an account exists.
- Do not weaken authentication, authorization, validation, or security checks to make tests pass.
- Treat JWT payloads as signed but not encrypted; do not place secrets in them.

## Tooling

- Use `uv` for dependency management and project commands.
- Do not use `pip` directly unless explicitly requested.
- Do not manually edit `uv.lock`.
- Do not add dependencies unless they are necessary for the requested task.
- Explain newly introduced dependencies when they are not obvious.

## Testing

- Add or update tests when behavior changes.
- Run the narrowest relevant tests first.
- Run broader regression tests after focused tests pass when practical.
- Do not delete or weaken tests merely to make the suite pass.
- Report real test failures instead of hiding, bypassing, or silently working around them.

## Working Agreement

Before changing code:

- Inspect the relevant existing code first.
- Understand the current architecture and conventions before implementing.
- Identify the smallest set of files that actually need changes.

When implementing:

- Make the smallest change that fully satisfies the task.
- Keep changes scoped to the requested work.
- Do not refactor unrelated code.
- Do not introduce speculative abstractions for hypothetical future requirements.
- Preserve existing public API behavior unless the task explicitly changes it.
- Prefer clear, maintainable code over clever code.

After changing code:

- Run relevant validation or tests.
- Report which files were changed.
- Summarize the behavior implemented.
- Explain non-obvious technical decisions.
- Report remaining risks, assumptions, or failures clearly.

## Git

- Do not commit, push, rebase, reset, force-push, or modify Git history unless explicitly requested.
- Do not discard user changes.
- Keep generated secrets and local environment files out of version control.
